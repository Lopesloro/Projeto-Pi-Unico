RESUMO

O presente documento descreve o desenvolvimento do PC Builder AI, uma aplicação
Web do tipo Single Page Application (SPA) voltada para auxiliar usuários a
montarem computadores personalizados com o melhor custo-benefício disponível no
mercado brasileiro. O sistema foi construído com tecnologias de front-end — HTML5,
CSS3 e JavaScript puro (Vanilla JS) — complementado por um servidor leve em
Node.js com Express para autenticação de usuários e persistência via banco de
dados SQLite. O núcleo inteligente da aplicação integra-se à API Google Gemini
para gerar recomendações de configurações de hardware com base no orçamento e no
objetivo declarados pelo usuário, enquanto um módulo de verificação baseado em
regras lógicas em JavaScript garante a compatibilidade técnica entre os
componentes (socket de processador versus placa-mãe, tipo de memória RAM e
potência da fonte de alimentação). O catálogo de componentes é estruturado em
arquivo JSON (components.json), contendo processadores, placas de vídeo, memórias
e demais periféricos com seus respectivos preços e atributos técnicos. O
desenvolvimento seguiu metodologia ágil SCRUM, organizado em sprints focadas na
entrega incremental de funcionalidades. Os resultados demonstram que é possível
construir uma ferramenta funcional e acessível para orientação de compra de
hardware sem a necessidade de infraestruturas complexas, utilizando tecnologias
Web amplamente disponíveis.

Palavras-chave: montagem de computadores; custo-benefício; JavaScript; sistema
especialista; compatibilidade de hardware; API de inteligência artificial;
desenvolvimento front-end.

1  INTRODUÇÃO
================================================================================

1.1 Contexto

O mercado de hardware para computadores no Brasil atravessa um momento de
crescente complexidade para o consumidor final. A diversidade de componentes
disponíveis, somada à variação constante de preços causada por fatores como
oscilação cambial, escassez global de semicondutores e múltiplos canais de venda
— desde lojas físicas especializadas até marketplaces internacionais —, cria um
cenário desafiador para quem deseja montar um computador com o melhor
custo-benefício possível.

De acordo com dados da Associação Brasileira da Indústria Elétrica e Eletrônica
(ABINEE, 2023), o segmento de equipamentos de tecnologia da informação registrou
crescimento de demanda superior a 18% nos dois anos subsequentes à pandemia de
COVID-19, impulsionado pela consolidação do trabalho remoto e pelo crescimento do
mercado gamer nacional. Entretanto, a complexidade técnica envolvida na seleção
de componentes compatíveis permanece como barreira significativa para uma grande
parcela dos consumidores.

Questões como a compatibilidade entre o socket do processador e o slot da
placa-mãe, a correspondência entre o tipo de memória RAM suportada e a memória
adquirida (DDR4 versus DDR5), ou o cálculo correto da potência necessária para
a fonte de alimentação são detalhes técnicos que, quando ignorados, resultam em
compras incompatíveis, desperdício financeiro e frustração para o usuário.

Nesse contexto, ferramentas de apoio à decisão de compra de hardware tornam-se
instrumentos de grande valor social e econômico. Soluções como o PCPartPicker
(disponível internacionalmente) já demonstraram a viabilidade e a aceitação de
mercado para esse tipo de sistema, porém sem adaptação ao contexto brasileiro de
preços, lojas e realidade de orçamento do consumidor local.

1.2 Motivação — O Círculo Dourado (Simon Sinek)

Utilizando o framework do Círculo Dourado proposto por Simon Sinek em sua obra
"Comece pelo Porquê" (2009), o projeto pode ser compreendido em três camadas
concêntricas:

POR QUÊ: Acreditamos que qualquer pessoa, independentemente de seu conhecimento
técnico prévio, merece ter acesso a uma ferramenta que a oriente a investir seu
dinheiro com inteligência ao montar ou atualizar seu computador. O conhecimento
técnico não deve ser um privilégio de especialistas.

COMO: Desenvolvemos uma aplicação Web acessível, que combina uma base de dados
de componentes estruturada em JSON, regras lógicas de compatibilidade escritas
em JavaScript e integração com inteligência artificial generativa (Google Gemini)
para traduzir o orçamento e os objetivos do usuário em uma recomendação de
configuração personalizada e tecnicamente coerente.

O QUÊ: O PC Builder AI é uma Single Page Application que, a partir do orçamento
informado pelo usuário e de uma descrição textual do uso pretendido (jogos, edição
de vídeo, trabalho acadêmico etc.), gera uma lista de componentes compatíveis e
economicamente otimizada, exibida de forma clara e objetiva na tela.

1.3 Justificativa Acadêmica

Do ponto de vista da Engenharia de Software, o projeto representa a aplicação
prática de conceitos fundamentais da disciplina: análise e levantamento de
requisitos, modelagem de dados, arquitetura de sistemas, integração com APIs
externas, teste e validação. A escolha por tecnologias Web de base — HTML5, CSS3
e JavaScript — foi deliberada, alinhando-se ao perfil de um desenvolvedor
front-end júnior e demonstrando que soluções funcionais e com componentes de
inteligência artificial podem ser construídas sem dependência de frameworks
pesados ou infraestruturas de alto custo.

A adição de um servidor leve em Node.js com Express, responsável pela
autenticação de usuários e persistência em banco de dados SQLite, demonstra a
transição natural de uma aplicação puramente estática para um sistema com
camadas de segurança e persistência de dados, mantendo a simplicidade arquitetural
como princípio norteador.


================================================================================
2  OBJETIVOS
================================================================================

2.1 Objetivo Geral

Desenvolver uma aplicação Web do tipo Single Page Application (SPA) que auxilie
usuários a montarem configurações de computador personalizadas e tecnicamente
compatíveis, dentro do orçamento informado, utilizando JavaScript puro no
front-end, integração com a API Google Gemini para recomendações inteligentes e
um módulo de verificação de compatibilidade baseado em regras lógicas.

2.2 Objetivos Específicos

a) Estruturar um catálogo de componentes de hardware (processadores, placas de
   vídeo, memórias RAM, placas-mãe, fontes de alimentação e armazenamento) em
   formato JSON, com atributos técnicos e preços referenciados ao mercado
   brasileiro;

b) Implementar um módulo de verificação de compatibilidade em JavaScript,
   baseado em regras lógicas, capaz de validar a correspondência entre socket
   de processador e placa-mãe, compatibilidade de tipo de memória RAM e
   suficiência de potência da fonte de alimentação;

c) Integrar a API Google Gemini (modelo gemini-2.0-flash-lite) ao front-end
   para geração de recomendações de configuração personalizadas com base no
   orçamento e no objetivo de uso declarados pelo usuário;

d) Implementar sistema de autenticação de usuários (cadastro e login) por meio
   de servidor Node.js com Express e banco de dados SQLite, permitindo
   persistência de sessão via sessionStorage no navegador;

e) Desenvolver uma interface de usuário responsiva, intuitiva e multi-etapas
   (wizard) em HTML5 e CSS3, guiando o usuário desde o login até a exibição
   do resultado da recomendação;

f) Validar o sistema por meio de testes manuais de interface e testes unitários
   das funções de compatibilidade, garantindo a confiabilidade das regras
   implementadas;

g) Documentar o processo de desenvolvimento, a arquitetura adotada e os
   resultados obtidos, seguindo as normas da ABNT para trabalhos acadêmicos.

4.1 Sistemas Especialistas e Sistemas Baseados em Regras

Sistemas Especialistas são um ramo da Inteligência Artificial simbólica que
procura capturar e reproduzir o conhecimento de especialistas humanos em um
domínio específico, por meio de uma base de conhecimento e um mecanismo de
inferência. Segundo Russell e Norvig (2022, p. 293), "um sistema especialista é
um programa que aplica capacidades de raciocínio para chegar a uma conclusão",
funcionando de maneira análoga ao processo de tomada de decisão de um especialista
humano.

A forma mais clássica de representar o conhecimento em sistemas especialistas é
por meio de regras de produção, que seguem o formato SE-ENTÃO (IF-THEN). Nesse
modelo, cada regra representa um fragmento de conhecimento do especialista sobre
o domínio. O mecanismo de inferência percorre essas regras, avaliando quais
condições (premissas) são verdadeiras no contexto atual e disparando as ações
(conclusões) correspondentes.

No contexto do PC Builder AI, o módulo `compatibility.js` implementa um conjunto
de funções que materializam esse conceito. A função `verificarCompatibilidadeSocket`,
por exemplo, implementa a seguinte regra implícita:

    SE (cpu.socket == mobo.socket)
    ENTÃO (compatibilidade de processador e placa-mãe = VERDADEIRO)
    CASO CONTRÁRIO (compatibilidade = FALSO)

Da mesma forma, a função `verificarPotenciaFonte` implementa a regra:

    SE (fonte.potencia_w >= tdpTotal * 1.2)
    ENTÃO (fonte é suficiente = VERDADEIRO)
    CASO CONTRÁRIO (fonte é insuficiente = FALSO)

O fator 1.2 (margem de segurança de 20%) é conhecimento especialista
explicitamente codificado, refletindo a recomendação técnica de que fontes de
alimentação devem operar com margem de folga para garantir estabilidade e
longevidade. Esse tipo de conhecimento não é derivado de dados, mas sim
capturado diretamente da especialidade técnica do domínio.

A base de conhecimento do sistema é composta pelo arquivo `components.json`, que
contém os atributos técnicos de cada componente (socket, tipo de memória, TDP,
potência). O mecanismo de inferência, por sua vez, é composto pelas funções
JavaScript que consultam esses atributos e aplicam as regras de compatibilidade.

Essa arquitetura, embora mais simples que sistemas especialistas clássicos
baseados em motores de inferência dedicados (como o CLIPS ou o Drools), segue os
mesmos princípios fundamentais: separação entre base de conhecimento (dados) e
mecanismo de inferência (funções), e representação do conhecimento especialista
por meio de regras explícitas.

4.2 Desenvolvimento Web Front-end com JavaScript

O desenvolvimento front-end moderno tem como pilares três tecnologias
padronizadas pelo World Wide Web Consortium (W3C): HTML5 para estrutura semântica
do conteúdo, CSS3 para estilização e responsividade, e JavaScript para
comportamento dinâmico e interatividade.

O JavaScript, padronizado como ECMAScript pela ECMA International (atualmente na
especificação ES2023), evoluiu de uma linguagem de scripting simples para uma
linguagem de programação de propósito geral. Sua capacidade de executar
operações assíncronas por meio de Promises e da sintaxe async/await (introduzida
no ES2017) tornou-o capaz de consumir APIs externas de forma não-bloqueante,
sem necessidade de recarregamento da página.

O conceito de Single Page Application (SPA) refere-se a aplicações Web que
carregam uma única página HTML e atualizam dinamicamente seu conteúdo via
JavaScript, sem transições de página completa. Essa arquitetura proporciona
experiência de uso mais fluida e semelhante a aplicações desktop. No PC Builder AI,
a navegação entre etapas do formulário (Step 1 → Step 2) e a transição para a
tela de resultados são implementadas manipulando classes CSS e o estado do DOM
via JavaScript puro, sem dependência de frameworks como React ou Vue.

A especificação Fetch API, nativa dos navegadores modernos, permite ao JavaScript
realizar requisições HTTP assíncronas. No sistema desenvolvido, a Fetch API é
utilizada tanto para carregar o arquivo `components.json` localmente quanto para
enviar requisições à API Google Gemini e ao servidor Node.js local de
autenticação.

4.3 APIs de Inteligência Artificial Generativa

Os Modelos de Linguagem de Grande Escala (Large Language Models — LLMs) representam
um avanço significativo na área de processamento de linguagem natural. O Google
Gemini, especificamente o modelo `gemini-2.0-flash-lite` utilizado neste projeto,
pertence a essa categoria. Diferentemente dos sistemas especialistas clássicos,
que operam por regras explícitas e determinísticas, os LLMs aprendem padrões
estatísticos a partir de enormes volumes de texto e são capazes de gerar respostas
contextualizadas a partir de instruções em linguagem natural (prompts).

A integração entre sistemas baseados em regras e LLMs, como adotada neste
projeto, representa uma abordagem híbrida: as regras garantem correção lógica
e determinística para verificações críticas (compatibilidade de socket, por
exemplo), enquanto o LLM oferece flexibilidade para interpretar o objetivo do
usuário em linguagem natural e gerar uma recomendação personalizada e contextual.

Essa abordagem é conhecida na literatura como Neuro-Symbolic AI — a combinação
de métodos simbólicos (regras, lógica formal) com métodos conexionistas (redes
neurais, modelos de linguagem). Embora o projeto não implemente essa integração
em nível profundo, a coexistência de `compatibility.js` (simbólico) com a chamada
à API Gemini (conexionista) exemplifica conceitualmente essa tendência.

O servidor Node.js com Express, embora simples, adiciona uma camada de backend
responsável por autenticação de usuários com persistência em banco de dados SQLite.
Essa arquitetura cumpre requisitos de segurança básicos, separando a lógica de
autenticação do cliente (navegador) e evitando que credenciais sejam processadas
exclusivamente no front-end.

6.1 Análise dos Resultados do Benchmarking

A análise da tabela revela que o PC Builder AI apresenta diferenciais únicos
no segmento: é o único sistema, entre os analisados, que combina recomendação
por objetivo em linguagem natural com integração de inteligência artificial
generativa. Enquanto as soluções das lojas brasileiras (Kabum e Pichau) oferecem

respectiva loja e não oferecem personalização por objetivo de uso.

em dólares americanos e não possui versão adaptada ao mercado brasileiro.

A maior limitação identificada no PC Builder AI em relação ao PCPartPicker é a
necessidade de atualização manual dos preços no arquivo JSON, em contraste com
a atualização automática por scraping adotada pelo concorrente americano. Essa
limitação é reconhecida e endereçada nos trabalhos futuros (Seção 15).

8  PROTÓTIPOS DAS INTERFACES
================================================================================

Os protótipos das interfaces foram desenvolvidos em duas etapas: wireframes de
baixa fidelidade (sketches em papel na fase de concepção) e protótipos de alta
fidelidade implementados diretamente em HTML5 e CSS3 (abordagem code-as-prototype,
prática comum em equipes pequenas de front-end). A seguir, descreve-se cada tela
principal do sistema.

──────────────────────────────────────────────────────────────────────────────
8.1 Tela 1 — Login / Cadastro (index.html)

Descrição visual:
Tela centralizada com fundo escuro (tonalidade grafite/azul escuro, consistente
com estética gamer/tech). Contém um card central com:
- Logotipo ou nome "PC Builder AI" em destaque no topo.
- Subtítulo descritivo ("Entre para montar o setup dos seus sonhos").
- Campos de formulário: E-mail e Senha.
- Botão primário "Entrar" (ou "Cadastrar" no modo de criação de conta).
- Links secundários: "Criar conta" (alterna para modo cadastro) e "Esqueceu
  a senha?" (exibe alerta informativo).

Fluxo de navegação:
- Login bem-sucedido → redireciona para pages/builder.html.
- Cadastro bem-sucedido → recarrega a tela em modo login.
- Credenciais inválidas → exibe alerta com mensagem de erro.

Decisões de design:
- Fundo escuro foi escolhido para reduzir fadiga visual em uso noturno, comum
  no perfil gamer.
- O formulário alterna entre modo Login e Cadastro sem recarregar a página,
  aproveitando a dinâmica SPA do JavaScript.

──────────────────────────────────────────────────────────────────────────────
8.2 Tela 2 — Builder (pages/builder.html) — Etapa 1 de 2

Descrição visual:
Tela com cabeçalho identificando o sistema. Exibe uma barra de progresso
indicando "Passo 1 de 2". Contém:
- Campo numérico "Qual é o seu orçamento? (R$)" com placeholder "Ex: 3500".
- Mensagem de validação em vermelho abaixo do campo, exibida quando o valor
  é inferior a R$ 1.500,00.
- Botão "Próximo →" para avançar para a etapa 2.

Fluxo de navegação:
- Orçamento válido + clique em "Próximo" → avança para Etapa 2.
- Orçamento inválido → exibe mensagem de erro; permanece na Etapa 1.

──────────────────────────────────────────────────────────────────────────────
8.3 Tela 3 — Builder (pages/builder.html) — Etapa 2 de 2

Descrição visual:
Barra de progresso atualizada para "Passo 2 de 2" (100%). Contém:
- Área de texto "Para que você vai usar o PC?" com placeholder descritivo
  ("Ex: quero jogar Fortnite e editar vídeos curtos para o YouTube").
- Botão "← Voltar" (retorna à Etapa 1).
- Botão "Montar meu PC ✓" (submete o formulário e chama a API).

Estado de carregamento:
Durante a consulta à API Gemini, o botão de submissão é desabilitado e exibe
indicador de carregamento (spinner ou texto "Aguarde..."), prevenindo múltiplos
envios simultâneos.

──────────────────────────────────────────────────────────────────────────────
8.4 Tela 4 — Resultado (pages/resultado.html)

Descrição visual:
Tela que exibe o resultado da recomendação gerada pela IA. Contém:
- Título "Sua Configuração Recomendada" ou similar.
- Conteúdo HTML gerado pelo modelo Gemini: lista de componentes com justificativas
  de escolha, organizados em elementos <h3>, <ul>, <li> e <p>.
- Total estimado da configuração em destaque.
- Botão "← Fazer nova consulta" para retornar ao builder.

Estado de erro:
Caso a API retorne erro, a área de resultado exibe uma caixa de alerta em
vermelho com a mensagem de erro e instrução para nova tentativa.

──────────────────────────────────────────────────────────────────────────────
8.5 Notas sobre Responsividade

Todas as telas foram desenvolvidas com layout flexível utilizando Flexbox e
unidades relativas (rem, %, vh). A largura máxima do card central é limitada
a aproximadamente 480px em telas largas, centralizando o conteúdo. Em telas
menores que 480px (smartphones), o card ocupa 90% da largura da tela com

9  MODELO DE DADOS
================================================================================

O PC Builder AI opera com dois tipos de persistência de dados: dados estruturais
de componentes (armazenados em arquivo JSON estático) e dados de usuários
(armazenados em banco de dados SQLite via servidor Node.js). A seguir, descreve-se
a estrutura de cada um.

──────────────────────────────────────────────────────────────────────────────
9.1 Arquivo components.json

Localização: /data/components.json
Propósito: Catálogo completo de componentes de hardware disponíveis para
recomendação. Este arquivo constitui a base de conhecimento factual do sistema,
consultado tanto pelo módulo de compatibilidade quanto enviado integralmente
para a API Gemini como contexto de cada consulta.

Estrutura de alto nível:

{
  "processadores": [ ... ],
  "placas_video": [ ... ],
  "memorias_ram": [ ... ],
  "placas_mae": [ ... ],
  "fontes": [ ... ],
  "armazenamento": [ ... ]
}

Estrutura de um objeto PROCESSADOR:

{
  "id": "cpu_i3_12100f",
  "nome": "Intel Core i3-12100F",
  "marca": "Intel",
  "socket": "LGA1700",
  "tdp_w": 60,
  "video_integrado": false,
  "preco": 700.00
}

Atributos:
- id (string): Identificador único do componente. Formato: categoria_modelo.
- nome (string): Nome comercial completo do componente.
- marca (string): Fabricante do componente.
- socket (string): Tipo de socket físico (LGA1700, LGA1200, AM4, AM5 etc.).
  Atributo crítico para verificação de compatibilidade.
- tdp_w (number): Thermal Design Power em watts. Utilizado no cálculo de
  potência mínima da fonte de alimentação.
- video_integrado (boolean): Indica se o processador possui GPU integrada,
  relevante quando o usuário não inclui placa de vídeo dedicada.
- preco (number): Preço de referência em reais (R$). Atualizado manualmente.

Estrutura de um objeto PLACA-MÃE:

{
  "id": "mobo_b760m_aorus",
  "nome": "Gigabyte B760M AORUS Elite",
  "marca": "Gigabyte",
  "socket": "LGA1700",
  "tipo_memoria": "DDR5",
  "slots_m2": 2,
  "preco": 950.00
}

Atributos adicionais relevantes:
- tipo_memoria (string): Tipo de RAM suportado (DDR4 ou DDR5). Atributo crítico
  para verificação de compatibilidade com os módulos de memória.
- slots_m2 (number): Quantidade de slots M.2 disponíveis para SSD.

Estrutura de um objeto MEMÓRIA RAM:

{
  "id": "ram_8gb_ddr4_3200",
  "nome": "Memória RAM 8GB DDR4 3200MHz",
  "marca": "Kingston",
  "tipo": "DDR4",
  "capacidade_gb": 8,
  "frequencia_mhz": 3200,
  "preco": 180.00
}

Atributo crítico: tipo (string) — deve corresponder ao tipo_memoria da placa-mãe
para que a verificação de compatibilidade retorne verdadeiro.

Estrutura de um objeto FONTE DE ALIMENTAÇÃO:

{
  "id": "fonte_550w_80plus",
  "nome": "Fonte 550W 80 Plus Bronze",
  "marca": "Corsair",
  "potencia_w": 550,
  "certificacao": "80 Plus Bronze",
  "preco": 380.00
}

Atributo crítico: potencia_w (number) — deve ser maior ou igual a
(tdp_cpu + tdp_gpu) * 1.2 para que a verificação de potência retorne verdadeiro.

10  ARQUITETURA E TECNOLOGIAS
================================================================================

10.1 Visão Geral da Arquitetura

O PC Builder AI adota uma arquitetura cliente-servidor simplificada, em que o
cliente (navegador) concentra a maior parte da lógica da aplicação (arquitetura
front-end pesada), e o servidor tem responsabilidade restrita à autenticação e
persistência de usuários.

Essa escolha arquitetural reflete o perfil do projeto — uma aplicação desenvolvida
por uma equipe júnior de front-end — e favorece a simplicidade de implantação:
o sistema pode ser executado localmente com o comando `npm start`, sem necessidade
de infraestrutura de nuvem.

Camadas da arquitetura:

1. Camada de Apresentação (HTML5 + CSS3):
   Responsável pela estrutura e estilização das interfaces. Arquivos:
   - index.html: Tela de login/cadastro.
   - pages/builder.html: Tela do formulário de consulta.
   - pages/resultado.html: Tela de exibição dos resultados.
   - pages/style.css: Folha de estilos compartilhada.

2. Camada de Lógica de Negócio (JavaScript Vanilla — ES2017+):
   Responsável pelo comportamento dinâmico, validações e integração com APIs.
   Arquivos:
   - js/login.js: Lógica de autenticação (cadastro e login via API REST local).
   - js/main.js: Lógica do builder (navegação entre etapas, validações, chamada
     à IA).
   - js/ai.js: Módulo de comunicação com a API Google Gemini.
   - js/compatibility.js: Módulo de regras de compatibilidade de hardware.

3. Camada de Dados (JSON + SQLite):
   - data/components.json: Base de conhecimento de componentes (somente leitura
     pelo front-end).
   - usuarios.db: Banco de dados SQLite para usuários (leitura/escrita pelo
     servidor).

4. Camada de Servidor (Node.js + Express):
   Servidor HTTP leve responsável por:
   - Servir os arquivos estáticos do front-end (HTML, CSS, JS).
   - Expor os endpoints REST de autenticação (/api/login, /api/cadastro).
   - Gerenciar a conexão com o banco de dados SQLite.

5. Serviços Externos:
   - Google Gemini API: LLM para geração de recomendações de hardware.

10.3 Fluxo de Dados — Consulta de Configuração

O fluxo completo de uma consulta de recomendação segue as seguintes etapas:

Passo 1: O usuário acessa index.html e realiza login.
Passo 2: login.js envia POST /api/login ao servidor Node.js com email e senha.
Passo 3: server.js consulta a tabela Usuarios no SQLite e retorna sucesso/erro.
Passo 4: Em caso de sucesso, login.js salva { id, email } na sessionStorage e
         redireciona para pages/builder.html.
Passo 5: main.js carrega pages/builder.html. O usuário preenche orçamento (Passo 1)
         e objetivo (Passo 2) do wizard.
Passo 6: Ao submeter, main.js executa fetch('../data/components.json') para
         carregar o catálogo de peças.
Passo 7: main.js chama consultarIA(orcamento, objetivo, estoque) do módulo ai.js,
         passando os três parâmetros.
Passo 8: ai.js monta o prompt com os dados e envia POST à Gemini API com
         autenticação via API Key.
Passo 9: O modelo Gemini processa o prompt e retorna HTML com a recomendação.
Passo 10: ai.js retorna o HTML para main.js, que o salva na sessionStorage
          (chave 'resultadoIA') e redireciona para pages/resultado.html.
Passo 11: resultado.html lê a sessionStorage e insere o HTML da recomendação
          no DOM via innerHTML.

POST /api/cadastro  → Cria novo usuário. Body: { email, senha }.

11  DESCRIÇÃO DA SOLUÇÃO DE IA
================================================================================

11.1 Visão Geral

O PC Builder AI implementa uma abordagem híbrida de inteligência artificial,
combinando dois paradigmas complementares:

a) Sistema Baseado em Regras (Rule-Based System): módulo `compatibility.js`,
   responsável pela verificação determinística e lógica de compatibilidade
   entre componentes de hardware.

b) Modelo de Linguagem de Grande Escala (LLM): integração com a API Google
   Gemini, responsável pela interpretação do objetivo em linguagem natural e
   pela geração da recomendação personalizada de configuração.

Essa combinação atende a diferentes necessidades cognitivas do problema:
verificações lógicas binárias (compatível/incompatível) são melhor tratadas por
regras explícitas, enquanto a interpretação de intenção do usuário e a
otimização multiobjetivo (orçamento + performance + objetivo de uso) beneficiam-se
da capacidade generativa dos LLMs.

──────────────────────────────────────────────────────────────────────────────
11.2 Módulo de Regras de Compatibilidade (compatibility.js)

O arquivo compatibility.js implementa três funções, cada uma representando um
conjunto de regras do domínio de hardware:

11.2.1 Função verificarCompatibilidadeSocket

Propósito: Verificar se o processador escolhido é fisicamente compatível com
a placa-mãe, por meio da correspondência do tipo de socket.

Regra implementada:
    SE cpu.socket IGUAL A mobo.socket
    ENTÃO retornar VERDADEIRO (compatível)
    CASO CONTRÁRIO retornar FALSO (incompatível)

Base de conhecimento consultada: atributo "socket" dos objetos processador e
placa-mãe no components.json.

Exemplos de pares compatíveis:
- Intel Core i3-12100F (LGA1700) + Gigabyte B760M (LGA1700) → COMPATÍVEL
- Intel Core i5-9400F (LGA1151) + Placa-mãe B760M (LGA1700) → INCOMPATÍVEL

11.2.2 Função verificarCompatibilidadeMemoria

Propósito: Verificar se o tipo de memória RAM é suportado pela placa-mãe.

Regra implementada:
    SE ram.tipo IGUAL A mobo.tipo_memoria
    ENTÃO retornar VERDADEIRO (compatível)
    CASO CONTRÁRIO retornar FALSO (incompatível)

Base de conhecimento consultada: atributo "tipo" do objeto RAM e atributo
"tipo_memoria" do objeto placa-mãe no components.json.

Exemplos:
- RAM DDR4 3200MHz + Placa-mãe que suporta DDR4 → COMPATÍVEL
- RAM DDR5 5600MHz + Placa-mãe que suporta DDR4 → INCOMPATÍVEL

11.2.3 Função verificarPotenciaFonte

Propósito: Verificar se a fonte de alimentação tem potência suficiente para o
conjunto processador + placa de vídeo, com margem de segurança.

Regra implementada:
    tdpMinimo = (tdp_cpu + tdp_gpu) * 1.2
    SE fonte.potencia_w MAIOR OU IGUAL A tdpMinimo
    ENTÃO retornar VERDADEIRO (fonte suficiente)
    CASO CONTRÁRIO retornar FALSO (fonte insuficiente)

O fator 1.2 representa a margem de segurança de 20% recomendada por fabricantes
de fontes de alimentação, garantindo operação estável e prolongando a vida útil
do componente.

Exemplo de cálculo:
    CPU TDP: 60W (i3-12100F)
    GPU TDP: 115W (RTX 3050)
    TDP Total: 175W
    TDP Mínimo com margem: 175 * 1.2 = 210W
    Fonte 550W 80 Plus Bronze: 550 >= 210 → VERDADEIRO

──────────────────────────────────────────────────────────────────────────────
11.3 Módulo de IA Generativa (ai.js + API Google Gemini)

11.3.1 Arquitetura do Prompt (Prompt Engineering)

O módulo ai.js implementa uma técnica de prompt engineering conhecida como
"few-shot contextual prompting" — fornece ao modelo um papel (persona), um
contexto (dados do estoque), uma tarefa específica (escolher peças dentro do
orçamento) e restrições explícitas (não inventar peças, usar apenas HTML).

Estrutura do prompt construído em ai.js:

"Você é um especialista em montagem de computadores com anos de experiência.
Um cliente te procurou com o seguinte pedido:
- Orçamento máximo: R$ {orcamento}
- Objetivo/Uso do PC: '{objetivo}'

Aqui está o nosso estoque de peças em formato JSON:
{JSON.stringify(estoque)}

Sua tarefa:
1. Analise o estoque e escolha as melhores peças que se encaixem no orçamento.
2. É OBRIGATÓRIO garantir a compatibilidade (ex: Socket da placa-mãe DEVE bater
   com o processador).
3. Se o orçamento for muito baixo, tente focar no essencial primeiro.
4. NÃO USE MARKDOWN. Retorne a resposta APENAS usando tags HTML válidas.
5. Explique brevemente por que você escolheu essas peças para o objetivo.
6. No final, mostre o valor total das peças selecionadas.

NÃO invente peças que não estão no JSON. Use apenas o que foi fornecido."

11.3.2 Análise das Decisões de Design do Prompt

Persona de especialista: Direciona o modelo para o domínio correto (hardware),
aumentando a precisão das escolhas e das justificativas técnicas.

Injeção do estoque em JSON: Garante que o modelo trabalhe apenas com peças
reais e preços corretos, eliminando o risco de "alucinação" de peças inexistentes
(uma limitação conhecida dos LLMs quando operam sem contexto).

Restrição de formato (HTML, sem Markdown): Garante que a saída seja diretamente
renderizável no DOM do navegador via innerHTML, sem necessidade de parsing
adicional.

Restrição de não inventar peças: Instrução explícita de grounding (ancoragem
em fatos), técnica de prompt engineering que reduz significativamente a tendência
dos LLMs de gerar informações fabricadas.

11.3.3 Modelo Utilizado e Justificativa

O modelo gemini-2.0-flash-lite foi escolhido por:
a) Custo-benefício: Modelo de menor custo na família Gemini, adequado para um
   projeto acadêmico sem orçamento para APIs pagas em larga escala.
b) Velocidade: Tempo de resposta inferior ao dos modelos maiores da família
   Gemini Pro, mantendo a experiência do usuário responsiva.
c) Capacidade suficiente: Para a tarefa de seleção e justificativa de
   componentes a partir de um catálogo JSON, o modelo lite demonstrou resultados
   satisfatórios nos testes realizados.

11.3.4 Tratamento de Erros

O módulo ai.js implementa tratamento de erros em dois níveis:
- Erro HTTP da API (status != 200): Extrai a mensagem de erro do campo
  dados.error.message e propaga para o front-end.
- Ausência de conteúdo na resposta: Verifica se dados.candidates[0].content
  .parts[0].text existe antes de retornar, lançando erro descritivo caso
  a estrutura esteja ausente.

Em ambos os casos, o front-end exibe uma caixa de erro estilizada em vermelho
com a mensagem específica, orientando o usuário a tentar novamente.

──────────────────────────────────────────────────────────────────────────────
11.4 Interação Entre os Dois Módulos de IA

No fluxo atual, o módulo compatibility.js e o módulo ai.js são utilizados de
forma complementar: a verificação de compatibilidade está instruída dentro do
prompt enviado ao Gemini (item 2 da tarefa), enquanto as funções de
compatibility.js estão disponíveis para validação independente no cliente.

Em versões futuras, o fluxo ideal seria:
1. O usuário seleciona manualmente um conjunto de componentes.
2. compatibility.js valida cada par (CPU-Mobo, RAM-Mobo, Fonte-TDP).
3. Apenas se todos os pares forem compatíveis, o sistema confirma a configuração.
4. Opcionalmente, a API Gemini pode ser consultada para sugestões de otimização.

Essa evolução transformaria o sistema em um assistente de montagem verdadeiramente
híbrido, com validação determinística garantida pelas regras e orientação
contextual provida pelo LLM.

12.4 Limitações Identificadas nos Testes

Durante a fase de testes, foram identificadas as seguintes limitações que não
constituem defeitos críticos, mas devem ser endereçadas em versões futuras:

L-01: A chave da API Google Gemini está exposta diretamente no arquivo ai.js
      (front-end). Embora funcional, essa prática expõe a chave no código-fonte
      acessível via DevTools. Mitigação prevista: rotear a chamada à API através
      do servidor Node.js como proxy, ocultando a chave no back-end.

L-02: Senhas armazenadas em texto simples no banco SQLite. Previsto: implementação
      de hash com bcrypt.

L-03: O tempo de resposta da API Gemini pode exceder 10 segundos em horários
      de pico, o que pode ser percebido como travamento pelo usuário caso o
      indicador de carregamento não seja suficientemente visível.

L-04: Não há mecanismo de logout explícito. O usuário encerra a sessão ao fechar
      o navegador (sessionStorage é limpa automaticamente).

14.4 Discussão das Limitações

A principal limitação técnica identificada refere-se à exposição da chave da
API Google Gemini diretamente no código front-end (ai.js). Em uma aplicação
comercial, essa prática seria inaceitável do ponto de vista de segurança, pois

utilizá-la com custos atribuídos ao titular da conta. Para o contexto acadêmico
e de demonstração, o risco é gerenciável, mas a mitigação definitiva — roteamento
da chamada à API através do servidor Node.js como proxy — está prevista como
primeira prioridade nos trabalhos futuros.

A segunda limitação significativa é a atualização manual dos preços no arquivo
components.json. Em condições de mercado com alta volatilidade de preços (comum
no segmento de hardware no Brasil), um catálogo desatualizado pode gerar
recomendações com valores distantes da realidade. Soluções automáticas de
atualização de preços exigem integração com APIs de lojas (quando disponíveis)
ou técnicas de web scraping, que aumentam significativamente a complexidade do
sistema.

A terceira limitação reside no armazenamento de senhas em texto simples no banco
de dados SQLite. Embora o sistema esteja no escopo de um projeto acadêmico, a
ausência de hash de senha representa uma vulnerabilidade crítica que deve ser
corrigida antes de qualquer implantação em ambiente de produção.

15  CONCLUSÃO E TRABALHOS FUTUROS
================================================================================

15.1 Conclusão

O presente projeto demonstrou a viabilidade do desenvolvimento de uma aplicação
Web funcional, com componentes de inteligência artificial, utilizando tecnologias
de front-end acessíveis e uma infraestrutura de back-end leve. O PC Builder AI
atingiu seus objetivos principais: guiar usuários sem conhecimento técnico na
seleção de componentes de hardware compatíveis e economicamente adequados ao
seu orçamento.

Do ponto de vista da Engenharia de Software, o projeto propiciou a aplicação
prática de um conjunto abrangente de conceitos: levantamento de requisitos com
usuários reais, modelagem de dados, arquitetura de sistemas, integração com APIs
externas (REST e LLM), desenvolvimento iterativo com SCRUM, testes unitários e
manuais, e documentação técnica segundo normas acadêmicas.

A combinação de um sistema baseado em regras determinísticas (compatibility.js)
com um modelo de linguagem generativo (Gemini API) demonstrou ser uma abordagem
eficaz para o domínio de compatibilidade de hardware: as regras garantem correção
lógica nas verificações binárias, enquanto o LLM oferece flexibilidade e
naturalidade na interpretação do objetivo do usuário e na geração da resposta.

O feedback positivo dos três representantes da comunidade externa, incluindo um
profissional técnico com mais de uma década de experiência na área, validou tanto
a utilidade prática da ferramenta quanto a qualidade das recomendações geradas.

A experiência também evidenciou as limitações naturais de um projeto desenvolvido
em nível júnior, como a exposição da chave de API no front-end e o armazenamento
não seguro de senhas, que servirão como motivação para aprofundamento técnico
nos semestres subsequentes.

15.2 Trabalhos Futuros

Com base nas limitações identificadas e nas oportunidades de evolução observadas,
os seguintes trabalhos futuros são propostos em ordem de prioridade:

1. Proxy de API no Back-end: Mover a chamada à API Google Gemini para o servidor
   Node.js, eliminando a exposição da chave de API no front-end. Esse é o trabalho
   futuro de maior impacto em segurança.

2. Hash de Senhas com Bcrypt: Implementar a biblioteca bcrypt no servidor para
   armazenar senhas de forma segura, aplicando salt e hash antes da gravação no
   banco de dados.

3. Atualização Automática de Preços: Desenvolver um módulo de integração com
   a API pública da Kabum ou da Amazon Brasil para atualização automática dos
   preços no catálogo, eliminando a dependência de atualização manual.

4. Seleção Manual de Componentes: Implementar uma interface onde o usuário possa
   selecionar manualmente os componentes desejados e o sistema verifique a
   compatibilidade em tempo real, utilizando as funções do módulo compatibility.js.

5. Histórico de Configurações: Utilizar o banco de dados SQLite existente para
   salvar o histórico de configurações consultadas por cada usuário, com
   visualização em uma tela dedicada.

6. Evolução para Back-end Completo: Migrar gradualmente a lógica de negócio do
   front-end para um servidor Node.js com Express mais robusto, com camada de
   serviço separada da camada de rotas, preparando a arquitetura para escalabilidade.

7. Testes Automatizados de Interface: Implementar testes end-to-end com Playwright
   ou Puppeteer para automatizar os cenários de teste manuais e reduzir o esforço
   de regressão a cada nova versão.

8. Comparação de Preços Multi-Loja: Expandir o catálogo para conter múltiplos
   preços por componente (Kabum, Pichau, Terabyte Shop), exibindo o menor preço
   disponível para cada peça recomendada.

APÊNDICE A — RESPOSTAS ÀS DIRETRIZES DE ORIENTAÇÃO ESPECÍFICA
Diretriz E: Sistemas Baseados em Regras ou Sistemas Especialistas
================================================================================

Nota: Este apêndice responde exclusivamente às questões da diretriz "E. Sistemas
Baseados em Regras ou Sistemas Especialistas" do roteiro de Orientação Específica
do Projeto Integrador V.

──────────────────────────────────────────────────────────────────────────────
E.1 O que é um Sistema Especialista e como ele se enquadra neste projeto?

Um Sistema Especialista é um programa de computador que emula a capacidade
decisória de um especialista humano em um domínio específico e restrito,
utilizando uma base de conhecimento formalizada e um mecanismo de inferência para
chegar a conclusões. Foram amplamente pesquisados e desenvolvidos a partir da
década de 1970, sendo DENDRAL (diagnóstico de estruturas moleculares) e MYCIN
(diagnóstico de infecções bacterianas) os exemplos históricos mais citados.

No PC Builder AI, o domínio restrito é a compatibilidade de hardware para
computadores pessoais. O módulo compatibility.js implementa os elementos
fundamentais de um sistema especialista simples:

- Base de Conhecimento: O arquivo components.json contém os fatos sobre os
  componentes (seus atributos técnicos: socket, tipo de memória, TDP, potência).
  Esses fatos são o equivalente aos "fatos da memória de trabalho" em um sistema
  especialista clássico.

- Base de Regras: As funções do módulo compatibility.js codificam o conhecimento
  especialista sobre compatibilidade de hardware na forma de regras IF-THEN
  (SE-ENTÃO):
  * SE cpu.socket == mobo.socket → ENTÃO compatível
  * SE ram.tipo == mobo.tipo_memoria → ENTÃO compatível
  * SE fonte.potencia_w >= tdpTotal * 1.2 → ENTÃO fonte suficiente

- Mecanismo de Inferência: A lógica de execução das funções JavaScript constitui
  o mecanismo de inferência: dado um conjunto de fatos (atributos dos componentes
  consultados no JSON), as regras são avaliadas e uma conclusão (verdadeiro ou
  falso) é produzida.

──────────────────────────────────────────────────────────────────────────────
E.2 Qual é a Base de Conhecimento do sistema e como foi construída?

A base de conhecimento do PC Builder AI é composta por duas partes:

Parte 1 — Fatos (components.json):
Contém as características técnicas objetivas de todos os componentes de hardware
disponíveis no catálogo. Esses fatos foram levantados por pesquisa em fontes
técnicas confiáveis: Intel ARK Database (especificações de processadores Intel),
AMD Product Specifications (processadores AMD), e fichas técnicas dos fabricantes
de placas de vídeo (NVIDIA, AMD).

Os atributos críticos para compatibilidade foram identificados e incluídos
explicitamente em cada objeto JSON: socket (nos processadores e placas-mãe),
tipo_memoria (nas placas-mãe) e tipo (nas memórias RAM), além de tdp_w
(processadores e placas de vídeo) e potencia_w (fontes de alimentação).

Parte 2 — Regras (compatibility.js):
Contém o conhecimento heurístico e especialista sobre como os componentes devem
se relacionar para funcionar corretamente juntos. Esse conhecimento foi obtido
a partir do domínio de especialidade dos integrantes da equipe com maior
conhecimento técnico em hardware e validado com o representante Rodrigo Ferreira
(técnico com 12 anos de experiência em montagem de PCs).

──────────────────────────────────────────────────────────────────────────────
E.3 Como as regras de inferência são representadas no código?

As regras são representadas como funções JavaScript com estruturas condicionais
(if/else e operadores lógicos). Cada função recebe objetos JavaScript como
parâmetros (que carregam os atributos técnicos do componente consultado via JSON)
e retorna um booleano (verdadeiro = compatível, falso = incompatível).

Exemplo concreto da regra de compatibilidade de socket:

  function verificarCompatibilidadeSocket(cpu, mobo) {
      if (!cpu || !mobo) return false;  // Guarda: objetos nulos = incompatível
      return cpu.socket === mobo.socket; // Regra principal: igualdade de socket
  }

O operador === (igualdade estrita) garante que a comparação seja feita tanto
por valor quanto por tipo, evitando comparações incorretas por coerção de tipo
do JavaScript.

──────────────────────────────────────────────────────────────────────────────
E.4 Como os dados do JSON são validados pelos blocos de decisão em JavaScript?

O fluxo de validação segue os seguintes passos:

Passo 1: Carregamento da base de fatos
O arquivo components.json é carregado via Fetch API no início da execução do
builder. Seus objetos são parseados pelo método JSON.parse (nativo no retorno
da Fetch API com .json()) e armazenados em variáveis JavaScript.

Passo 2: Seleção dos objetos a verificar
Para verificar compatibilidade entre dois componentes, os objetos correspondentes
são localizados no array carregado do JSON usando Array.find() com o id como
chave de busca:
  const cpu = processadores.find(p => p.id === "cpu_i3_12100f");
  const mobo = placas_mae.find(m => m.id === "mobo_b760m_aorus");

Passo 3: Aplicação das regras
Os objetos localizados são passados como argumentos para as funções do módulo
compatibility.js:
  const socketOk = verificarCompatibilidadeSocket(cpu, mobo);
  const memoriaOk = verificarCompatibilidadeMemoria(ram, mobo);
  const fonteOk = verificarPotenciaFonte(fonte, tdpCpu + tdpGpu);

Passo 4: Interpretação dos resultados
Os booleanos retornados determinam o fluxo de exibição: configurações com
incompatibilidades devem ser sinalizadas ao usuário com mensagem descritiva.

──────────────────────────────────────────────────────────────────────────────
E.5 Quais são as limitações do Sistema Especialista implementado e como poderiam
    ser superadas?

Limitação 1 — Cobertura parcial das regras de compatibilidade:
O sistema atual verifica três dimensões de compatibilidade (socket, memória e
potência). Existem outras dimensões relevantes não cobertas: compatibilidade
de velocidade de memória (XMP/EXPO), limite de TDP suportado pela placa-mãe
(VRM), compatibilidade de tamanho físico (form factor ATX, Micro-ATX, Mini-ITX),
e capacidade máxima de RAM suportada.
Solução: Ampliar o módulo compatibility.js com novas funções e enriquecer os
objetos no components.json com os atributos correspondentes.

Limitação 2 — Ausência de raciocínio encadeado (forward chaining):
O sistema atual aplica cada regra de forma independente, sem encadeamento entre
conclusões intermediárias. Um sistema especialista mais sofisticado poderia usar
uma conclusão de uma regra como premissa de outra.
Solução: Implementar um motor de inferência simples com encadeamento, onde a
verificação de compatibilidade de socket (Regra 1) desabilita automaticamente
as verificações subsequentes em caso de falha.

Limitação 3 — Base de regras estática:
As regras estão codificadas diretamente nas funções JavaScript. Para adicionar
uma nova regra, é necessário modificar o código-fonte.
Solução: Mover as regras para um arquivo regras.json, criando um motor de
inferência genérico que leia e execute as regras dinamicamente. Isso separaria
completamente a base de conhecimento do mecanismo de inferência, característica
fundamental dos sistemas especialistas clássicos.

──────────────────────────────────────────────────────────────────────────────
E.6 Como a solução de IA Generativa (Google Gemini) complementa o Sistema
    Especialista?

Os Sistemas Especialistas baseados em regras são excelentes para raciocínio
determinístico em domínios fechados e bem definidos, mas apresentam dificuldade
em lidar com entradas em linguagem natural não estruturada. A API Google Gemini,
por sua vez, é excelente para interpretar linguagem natural e gerar respostas
contextualizadas, mas não oferece garantias formais de correção lógica.

No PC Builder AI, essa complementaridade é explorada da seguinte forma:

- O Sistema Especialista (compatibility.js) é responsável pelas verificações
  binárias e formais: compatibilidade ou incompatibilidade. Não há ambiguidade
  nessas verificações.

- O Modelo Gemini é responsável pela interpretação do objetivo do usuário
  (linguagem natural) e pela otimização multiobjetivo (maximizar performance
  dentro do orçamento, considerando o uso pretendido). Tarefas que não se
  encaixam em regras IF-THEN simples.

Essa divisão de responsabilidades reflete um princípio importante em Engenharia
de Sistemas de IA: utilizar a ferramenta mais adequada para cada tipo de tarefa.
Regras determinísticas para verificações formais; modelos probabilísticos para
tarefas que envolvem interpretação e contexto.
